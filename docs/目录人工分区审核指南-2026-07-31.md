# 目录人工分区审核指南

## 1. 审核目标

本轮只审核真实目录的业务分区、菜品分类和可检索状态，不修改原始菜名、价格、位置、档口或来源。

数据库的固定位置层级是：

```text
一级场所/食堂 -> 餐厅或楼层 -> 档口 -> 目录条目
```

以下字段是菜品的并列属性，不是新的位置层级：

```text
业务类型：meal / snack / beverage / addon / fee / variant / section
菜品分类：米饭、面食、饺子、粥、汉堡、火锅等
餐次：breakfast / lunch / dinner / all_day / unknown
```

不要建立“早餐 -> 面食 -> 菜品”这种固定数据库层级。同一道面食可能同时属于早餐和午餐；饮品可能全天供应。

## 3. 可以修改的列

只填写以下列：

| 列 | 填写内容 |
|---|---|
| `confirmed_item_type` | 最终一级业务类型 |
| `confirmed_category` | 最终二级菜品分类 |
| `confirmed_meal_periods` | 早餐、午餐、晚餐、全天或未知，可多选 |
| `meal_period_source` | `menu`、`operator`、`official_policy` 或 `unknown` |
| `retrieval_status` | `include`、`exclude` 或 `review_required` |
| `action` | `keep`、`merge`、`rename`、`exclude` 或 `needs_manual_check` |
| `review_note` | 简短说明判断依据或待确认问题 |

餐次多选时使用英文值并用 `|` 分隔，例如：

```text
breakfast|lunch
```

## 4. 禁止修改的列

以下字段必须保持原样：

- `id_readonly`
- `name_readonly`
- `primary_venue`
- `restaurant_or_floor`
- `floor`
- `stall`
- `price_display_readonly`
- `pricing_mode_readonly`
- `source_files`
- `status_readonly`

稳定 ID 是后续回写数据库、生成差异报告和回滚的唯一依据。

## 5. 推荐审核顺序

每一行按以下顺序判断：

### 第一步：判断是否为独立菜品

- 规格、人数、容量、口味选项：`variant`，通常 `exclude`。
- 单加鸡蛋、丸子、肉类、面条、配菜：`addon`，通常 `exclude`，并记录所属档口。
- 打包费、餐盒费、服务费：`fee`，`exclude`。
- “五元以上区”“其他类”等菜单标题：`section`，`exclude`。
- 完整套餐，例如包含主食和配菜的套餐：可以是 `meal`。

### 第二步：判断业务类型

- `meal`：完整的一餐或可独立购买的主食套餐。
- `snack`：可独立购买的小吃、炸物、串类、汉堡单品等。
- `beverage`：饮料、奶茶、果汁、矿泉水等。
- `addon`：只作为加料或配菜使用，不能独立作为主菜检索。
- `fee`：费用条目。
- `variant`：规格、人数、容量、口味选项。
- `section`：目录标题或价格区间标题。

### 第三步：填写菜品分类

优先使用 `CategoryDictionary` 中已有分类。常用分类包括：

- 米饭套餐
- 面食粉类
- 早餐面点
- 粥类
- 饺子馄饨
- 火锅麻辣烫
- 火锅配菜
- 汉堡套餐
- 汉堡小吃
- 烧烤卤味小吃
- 甜品小吃
- 饮品
- 轻食简餐

分类只描述目录形态，不代表配方、营养、销量或供应事实。

### 第四步：填写餐次

只有在菜单、档口负责人或正式营业安排明确说明时才填写早餐、午餐或晚餐。

- 明确早餐供应：`breakfast`
- 明确午餐供应：`lunch`
- 明确晚餐供应：`dinner`
- 明确全天或不区分餐次：`all_day`
- 没有可靠资料：`unknown`
- 同时明确多个餐次：例如 `breakfast|lunch`

不能因为菜名像“面”“粥”“汉堡”就自行推断餐次。

### 第五步：填写检索状态

- `include`：允许进入学生端找菜和 RAG 检索。
- `exclude`：保留在目录审计中，但不作为独立菜品展示或检索。
- `review_required`：资料不足、归属不明、重复关系不清或需要负责人确认。

## 6. 特殊情况规则

### 低价条目

“丸子”“鸡蛋”“豆皮”“面条”等低价条目不能只根据价格判断。必须结合档口：

- 如果是麻辣烫、火锅档口的配菜：通常为 `addon` + `火锅配菜`。
- 如果是面档口可单独购买的加料：通常为 `addon` + `面食加购`。
- 如果是完整菜品的一部分且不能独立购买：`exclude`。
- 证据不足时填 `review_required`，不要猜测。

### 饮料和汉堡

- 可乐、茶饮、奶茶、矿泉水等：`beverage`。
- 完整汉堡套餐：`meal` + `汉堡套餐`。
- 单独鸡块、薯条、炸翅根等：通常为 `snack` + `汉堡小吃`，但以目录是否独立售卖为准。

### 同名菜品

跨档口同名不自动合并。只要档口、餐厅或价格不同，就保留不同稳定 ID；在备注中写明区别。

同一档口内只有在确认是重复录入时才使用 `merge`，不能仅因为菜名相同就合并。

## 7. 交付方式

1. 队友先拉取最新代码，并创建自己的分支，例如：

   ```bash
   git switch -c codex/manual-catalog-review
   ```

2. 审核文件通过私下文件传输、企业网盘或共享盘传递，不提交到 GitHub。
3. 队友只修改允许编辑的列，不直接连接生产 PostgreSQL，不修改服务器数据。
4. 完成后返回 XLSX 或 CSV 文件，并说明未完成的行。
5. 回收文件后由项目维护者执行稳定 ID 校验、差异审计、事务回写和回滚检查。
6. 数据库校验通过后，再对分类变化的菜品增量重建 RAG 文档和向量。

## 8. 完成标准

- 每条记录都有 `confirmed_item_type` 或明确的 `review_required`。
- 每条可检索记录都有 `confirmed_category`。
- 没有把加购、费用、规格和目录标题标为可检索独立菜品。
- 没有修改稳定 ID、原始名称、价格和位置。
- 没有凭菜名猜测餐次；没有证据的餐次填写 `unknown`。
- 同名跨档口记录没有被错误合并。
- 回写前先生成差异报告，确认总记录数仍为 2563 条。
