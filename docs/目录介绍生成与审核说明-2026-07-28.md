# 目录介绍生成与审核说明

## 作用范围

目录介绍按“菜品 -> 档口 -> 餐厅/楼层 -> 食堂”生成，只补充目录语义，不修改实体原有 `description`，也不生成配方、过敏安全、清真认证、精确营养、销量、营业时间、库存或今日供应事实。

当前真实目录快照包含 2,563 道菜、138 个档口和 14 个餐厅/食堂记录，共 2,715 个待介绍实体。42 个档口和 3 个场所没有菜品目录，必须保留 `MENU_MISSING` 边界。

## 本地流程

所有命令只操作 Git 忽略的隔离 SQLite 副本。Chat Key 仅设置在当前 PowerShell 进程，任务结束后关闭终端并撤销旧 Key。

```powershell
$env:AI_CHAT_BASE_URL='https://provider.example/v1'
$env:AI_CHAT_API_KEY='<temporary-key>'
$env:AI_CHAT_MODEL='deepseek-v4-flash'
```

离线批量生成可通过 `AI_CHAT_API_KEYS` 使用多个独立临时 Key，使用分号或换行分隔。生成器只在内存中轮询，报告仅记录匿名 `key-1/key-2` 槽位、连通耗时和用量，不保存 Key。多 Key 是否提升吞吐必须以阶梯探测为准，不能根据 Key 数量直接推算并发。

1. 从不可变目录创建副本并核对实体数：

```powershell
npm run generate:catalog-introductions -- --reset --prepare-only
```

2. 只执行并发 `1 -> 2 -> 4 -> 6` 阶梯探测，保存已通过候选后暂停：

```powershell
npm run generate:catalog-introductions -- --probe-only
```

3. 检查 `.rag-evals/catalog-introductions/catalog-introduction-v4.json` 中的成功率、`429`、p50/p95、Token 吞吐、安全并发和预计剩余时间。

报告中的每个波次同时包含 `repairedCount`、`providerRetryCount` 和 `failureReasons`。Schema、证据、边界、鉴权、限流和网络错误应按错误码分别处理，不能把模型内容错误混入服务商限流统计。

4. 确认探测结果后，从已完成实体继续全量生成：

```powershell
npm run generate:catalog-introductions -- --skip-probe
```

需要保守降并发时增加 `--start-concurrency=1`。Key 失效、网络中断或持续限流后可重复执行同一命令，不会为输入哈希未变化的实体重复创建介绍。

同一 `batchId` 只允许恢复相同租户、目录快照、提示词和模型。任一项变化都会返回 `CATALOG_INTRODUCTION_BATCH_ID_CONFLICT`，此时应重新准备新批次，不能把旧候选混入新目录。数据库重启本身不会改写目录时间或输入哈希。

## 自动验收

- 模型每次只返回严格 JSON，校验失败最多定向修复一次。
- 每句话必须引用当前实体的证据白名单。
- 菜品正文必须写出实体名称，并实际使用价格、位置、同档口菜品中的至少两类证据。
- 有菜单的档口和场所必须写出具体数量、代表菜、档口或下级场所，不能使用名称模板凑数。
- “招牌”等词只在它属于数据库原始菜名时允许原样引用；模型额外声称“本店招牌菜”仍会被拒绝。
- 目录归属只能写“收录、位于、归属档口”；把它写成“供应、售卖、有售、可购买或可下单”会被拒绝。
- `ENTITY_NAME_REVIEW_REQUIRED` 用于“3-4人份”等疑似规格型名称：介绍必须明确名称待核验，可信度降为 `low`，且不得使用软标签或同档口菜名推断具体品类。
- `semanticLabels` 和概念只允许进入推测性推荐文案，并明确写成“从目录标签看可能”，不得升级为目录事实。
- 输入哈希、证据引用和实体名称覆盖率必须为 100%，有菜单实体不得出现完全相同介绍。
- 报告固定输出 200 条分层人工抽检样本，并包含全部餐厅和食堂。

## 展示与检索设计

- “标语”在产品中统一命名为“目录定位”。它复用已审核的 `recommendationCopy`，通过兼容字段 `positioningStatement` 和 `displayTagline` 返回，不新增一轮模型生成，也不把营销措辞升级为事实。
- 顶层场所、餐厅/楼层和档口在导航页同时展示事实摘要与目录定位；无菜单实体继续明确显示信息待补充，不根据名称推断经营特色。
- Web 菜品列表只展示名称、位置、价格、评分、供应状态和可信状态，点击后进入独立 `/dishes/:id` 详情页。旧 `/dishes?dish=<id>` 深链自动跳转，推荐、收藏和订单入口保持兼容。
- 菜品详情集中展示结构化价格、完整层级位置、目录定位、营养核验状态、过敏原边界、收藏、吃过、预约、评价和证据来源。小程序沿用已有独立详情页并统一“目录定位”文案。
- RAG 为 `venue` 和 `area` 文档增加“餐饮场所/食堂”和“餐厅/楼层/餐区”等层级词。菜品检索文档可以继承所属餐厅与顶层场所的已批准语义，但这些内容记录为 `locationSemanticEvidence`，不得覆盖菜品价格、配方、营养、过敏原或供应事实。
- 正式索引仍只读取 `approved` 介绍。当前 `2,715` 条候选没有批准，因此本次页面和索引能力已经就绪，但运行库不会提前展示或检索这些候选文案。

## 审核与发布

候选初始状态为 `schema_validated`，不会进入正式学生 RAG。`canteen_admin` 可以编辑、逐条批准或拒绝；只有 `tenant_admin`、`admin` 和 `super_admin` 可以整批操作。

生产导入必须使用完整 V4 文件 `data/real-catalog-introductions-deepseek-v4-dual-key-2026-07-29.sqlite`，并固定批次 `catalog-introduction-v4-deepseek-dual-key-2026-07-29` 与预期数量 `2715`。先执行 dry-run，保存输出中的源文件校验和与逻辑摘要；正式导入必须带回同一摘要。旧的 `real-catalog-introductions-2026-07-28.sqlite` 只包含早期探测候选，禁止用于生产。

整批批准前必须重新预览，并输入：

```text
批准全校介绍 <batchId>
```

任何实体输入哈希过期时整批返回 `409`。整批回滚需要输入：

```text
回滚介绍批次 <batchId>
```

批准或回滚通过 Outbox 更新菜品、档口和餐厅/食堂检索文档。正式索引只读取当前输入哈希仍有效的 `approved` 介绍；本地 A/B 才允许显式加载 `schema_validated`，并标记为 `ai_estimated`。
