# 智慧食堂 RAG 真实数据映射模板

## 1. 导入原则

- 小程序和 Web 只通过 Node API 访问同一租户数据库，不允许客户端直连数据库。
- 真实数据先进入 staging，完成格式、引用、租户和安全审核后才能发布。
- `synthetic` 必须为 `false`；生产导入器遇到 `synthetic=true` 应直接拒绝。
- 未提供的安全信息一律映射为 `unknown`，不能映射为 `confirmed_absent`。
- 菜品原型、通用知识和模型推断只能用于软语义，不能补造价格、配方、营养、供应或过敏原事实。

## 2. 最低可用字段

| 业务字段 | 目标字段 | 必填 | 规则 |
| --- | --- | --- | --- |
| 学校/租户 ID | `tenant_id` | 是 | 稳定且不可跨学校复用 |
| 食堂 ID | `canteen_id` | 是 | 必须属于当前租户 |
| 档口 ID | `stall_id` | 是 | 必须属于当前食堂和租户 |
| 菜品 ID | `id` | 是 | 租户内稳定，禁止用菜名作唯一键 |
| 菜名 | `name` | 是 | 保留原名；别名单独维护 |
| 状态 | `status` | 是 | 仅 `active` 可参与检索与推荐 |
| 当前价格 | 菜单项 `price` | 是 | 实时价格不写入向量文本 |
| 菜单日期/餐次 | `menus.date/meal_type` | 是 | 用于当前供应过滤 |
| 售罄/供应量 | `menu_items` 供应字段 | 建议 | 缺失时不得宣称可下单 |

## 3. 食品事实字段

| 源数据 | 目标字段 | 状态要求 |
| --- | --- | --- |
| 主配料 | `ingredients_json` | 配方未知时使用空数组并标 `recipe_fact_status=unknown` |
| 调味料 | `seasonings_json` | 与主配料分离 |
| 添加物 | `additives_json` | 与调味料分离 |
| 过敏原声明 | `safety_declarations_json` | 每项包含编码、状态、来源和版本 |
| 清真 | `halal` + `halal_fact_status` | 无证据不能标 `verified` |
| 饮食模式 | `dietary_labels_json` + `dietary_fact_status` | 仅结构化标签参与硬过滤 |
| 辣度 | `spice_level` + `spice_fact_status` | 0–5；未知用 `NULL` |
| 营养 | 热量、蛋白质、脂肪、碳水等 | 零值不能自动解释为低含量 |
| 营养状态 | `nutrition_fact_status` | `unknown/estimated/verified` |
| 配方状态 | `recipe_fact_status` | `unknown/estimated/verified` |

## 4. 过敏原声明对象

```json
{
  "allergenCode": "peanut",
  "status": "confirmed_present",
  "source": "stall_recipe_audit",
  "reviewedBy": "food-safety-role-id",
  "verifiedAt": "2026-07-26T08:00:00+08:00",
  "expiresAt": "2026-10-26T08:00:00+08:00",
  "dataVersion": "school-menu-2026.07"
}
```

允许状态及导入规则：

- 明确配方包含：`confirmed_present`
- 审核确认不含：`confirmed_absent`
- 无记录或证据不足：`unknown`
- 共用设备、油锅或操作台：`cross_contact_possible`

旧 `allergens_json` 非空项回填为 `confirmed_present`；旧空数组回填通配 `unknown`，绝不回填为“不含”。

## 5. 来源与版本字段

每道菜应提供：

- `fact_source`：档口配方、供应商标签、实验室、营养估算或旧系统。
- `fact_verified_at`：最近核验时间。
- `fact_expires_at`：声明失效时间；没有长期有效证据时建议填写。
- `data_version`：学校数据批次或审核版本。
- 审核人：安全声明内记录角色或脱敏 ID。

建议来源等级从高到低为：学校食品安全审核、供应商标签/检测、档口负责人确认、营养估算、名称推断。最后一类不得用于安全硬结论。

## 6. 推荐 CSV 表头

```text
tenant_id,canteen_id,stall_id,dish_id,name,status,cuisine,taste,ingredients,seasonings,additives,dietary_labels,halal,spice_level,calories,protein,fat,carbs,fiber,sodium,sugar,nutrition_fact_status,recipe_fact_status,halal_fact_status,dietary_fact_status,spice_fact_status,fact_source,fact_verified_at,fact_expires_at,data_version
```

过敏原声明建议使用单独关联表，避免在 CSV 单元格中维护复杂 JSON：

```text
tenant_id,dish_id,allergen_code,status,source,reviewed_by,verified_at,expires_at,data_version
```

菜单和供应使用独立表：

```text
tenant_id,menu_id,canteen_id,date,meal_type,status,dish_id,price,supply_limit,supply_count,sold_out,serving_start,serving_end,updated_at
```

## 7. 导入前校验清单

- 租户、食堂、档口、菜品外键全部可解析。
- 菜品 ID 在租户内唯一；跨租户同 ID 不会相互覆盖。
- 金额、营养和辣度范围合法，零营养值按未知处理。
- 所有安全状态、事实状态和饮食标签属于枚举。
- `confirmed_absent` 有审核来源、时间和审核人。
- 过期声明不会参与“已核验”展示。
- 菜单时间、状态、价格和库存冲突进入人工复核。
- 图片缺失不阻塞食品事实导入。
- 导入后增量重建当前租户菜品索引，不索引用户档案和评测查询。
- 发布前执行过敏原、跨租户、虚构事实和空结果回归。

## 8. 第一批真实数据建议

先提供一家学校 500–2,000 道菜和至少 30 天菜单。优先保证菜品位置、价格、餐次、供应、主配料、调味料、过敏原状态及来源完整；营养可以分批补录，但缺失时必须保持 `unknown`。同时提供 200–500 条脱敏真实查询，用于发现合成模板无法覆盖的别名、地方叫法和条件组合。
