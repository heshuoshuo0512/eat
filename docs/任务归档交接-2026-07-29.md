## 4. 产品与业务边界

### 4.1 当前产品定位

智慧食堂是校园餐饮信息、检索、推荐、社区和数据治理平台，包含学生 Web、微信小程序、管理端、Agent/RAG、可信拍照识餐和独立图片采集站。

正式目录层级统一为：

```text
一级场所
  -> 餐厅 / 楼层 / 餐区（按场所类型可跳过）
    -> 档口
      -> 菜品
```

### 4.2 已调整的业务假设

- 真实目录以学期内相对稳定的菜品目录为主，不再把演示“今日供应”当成所有菜品的真实状态。
- 当前主业务方向是目录浏览、检索、推荐和到店预约/到店支付。早期模拟在线支付、外卖和假库存不能当作当前生产事实。
- 代码中仍可能保留菜单、订单、模拟支付和兼容接口，继续开发前必须先确认其当前产品状态，不能因为接口存在就宣称功能已正式运营。
- 目录中没有已核验营业或预约状态时，前端和 Agent 必须明确显示未知、暂停预约或目录参考。

### 4.3 食品安全边界

- `confirmed_present` 和 `cross_contact_possible` 对严重过敏用户执行排除。
- `confirmed_absent` 必须有可靠审核来源，空数组和未标注不能解释为“不含”。
- `unknown` 必须显示未核验警告，不能给出“放心食用”结论。
- 营养、配方、清真、素食和辣度分别保留事实状态和来源；AI 估算只能作为软排序或待核验候选。
- 系统只提供一般饮食教育，不进行疾病诊断、治疗或个体医疗处方。

## 6. Agent 与 RAG

### 6.1 两条核心工作流

菜品查询与智能推荐必须保持独立：

| 工作流 | 入口与目标 | 关键约束 |
|---|---|---|
| 菜品查询 | 找名称、位置、价格和目录菜品 | 显式筛选优先，返回真实目录和可用性 |
| 智能推荐 | 结合档案和临时条件给出备选或组合 | 先执行过敏、忌口、清真、预算和供应硬约束 |

核心编排使用普通 JavaScript、Zod、SQL、`server/retrievalService.js`、`server/retrievalIndex.js` 和 `server/aiProvider.js`。当前生产主链不依赖 LangChain 或 LangGraph。

执行顺序固定为：

```text
身份、租户和权限
-> 规则与 SQL 硬过滤
-> 知识源路由
-> 精确 / 词法 / 向量并行召回
-> 分源 RRF 与结构化重排
-> 证据校验
-> 受引用约束的回答
```

价格、位置、供应、权限、过敏原和订单状态只能来自数据库；Embedding 和 Chat 模型不能覆盖这些事实。模型、额度或向量服务不可用时必须回退到精确/词法检索和确定性答案。

### 6.2 校园语义底座

- 500 个已审核校园饮食概念，固定分类配额为 220/90/60/40/40/30/20。
- 300 条冻结评测查询，不进入索引；另有独立挑战、真实目录和多知识源评测。
- 早期 10 所虚拟高校、5,000 道模拟菜只用于压力和故障测试，全部标记为 `synthetic`，不能当生产数据。

### 6.3 Qwen Embedding 结论

| 指标 | Qwen 0.6B / 1024维 | Qwen 8B FP16 / 4096维 |
|---|---:|---:|
| 目录混合检索 nDCG@10 | 0.9866 | 0.9943 |
| 目录完整工作流 P95 | 654.72ms | 43,450.33ms |
| 多知识源通过率 | 100% | 100% |
| 多知识源 nDCG@5 | 0.9318 | 0.9420 |
| 多知识源 P95 | 225.83ms | 8,347.53ms |

8B 的质量提升不足以覆盖延迟，目前推荐 Qwen3-Embedding 0.6B。增强组仍需要恰好 200 条有效 AI 预标注才能完成终评，不能使用 Mock 结果替代。

正式上线要求：

- 0.6B 为 1,024 维，8B 为 4,096 维；二者以及旧 `vector(1536)` 不能混用。
- 当前 PostgreSQL 迁移中仍保留旧 1,536 维列设计。正式启用 Qwen 前必须确定唯一模型和维度、迁移列、全量重建索引并验证回滚。
- 流量切换必须经过 `off -> shadow -> active`，不能根据单次局部测试直接切换生产排序。

### 6.4 受约束回答评测

- 旧模型直出基线：`59/85 = 69.41%`。
- V2 首轮最终：`84/85 = 98.82%`。

## 8. 拍照识餐与图片采集站

### 8.1 可信识餐 MVP

已实现的主链：

```text
用户拍照
-> 当前租户、场所、档口和菜单上下文过滤
-> SigLIP 图片向量召回
-> 多模态候选复核
-> Top 3 用户确认
-> 数据库配方/营养查询
-> 反馈与监控
```

固定边界：

- SigLIP 负责图片相似度，Qwen Embedding 负责文字和 RAG，两类向量不能混用。
- 图片本身通常不能可靠判断具体食堂或档口；位置归属必须来自用户上下文和目录关系。
- 未确认菜品前不返回可信营养；缺少审核配方时保持 `unknown` 或明确的估算区间。
- Top 3 召回率目标至少 95%，自动确认子集 Top 1 精确率至少 95%，错误食堂/档口归属必须为 0，端到端 P95 目标不超过 8 秒。

### 8.2 两级数据门槛

不要混淆“检索 MVP”与“微调模型”的数据量：

- 检索 MVP：每道菜至少 8 张 `reference` 图和 4 张严格隔离的 `evaluation` 图；先做 20 道菜闭环，再扩到单食堂 80-100 道高频菜。
- SigLIP 微调资格：每个 `dish_id` 至少 60 张审核通过图片，来自至少 10 个匿名贡献者；按贡献者隔离为约 40 训练、10 验证、10 测试。
- 大规模首版微调目标曾规划为 200 道高频菜、约 12,000 张合格图片；在小规模闭环和审核质量达标前不要直接追求该规模。

### 8.3 独立采集站

- 采集站已部署到 `https://collector.stueat.com`，与主站共用服务器和主域名的子域名，不需要第二台服务器。
- 采集站包含独立 Vue 页面、Node API、匿名贡献、每日限额、重复检测、审核、10% 复审、冲突裁决、数据集导出和模型注册/回滚。
- 图片上传后进行 EXIF/GPS 清除、尺寸限制、内容哈希和感知重复检查；正式图片保存在私有对象存储。
- 目录搜索调用自己的 Node API，不调用付费视觉模型；视觉建议是可选辅助，关闭后仍能通过菜名搜索、选择 `dish_id` 和人工审核完成采集。
- 训练标签以具体 `dish_id` 为主，规范菜名为辅助，食堂/档口只作为元数据。模型识别菜品后再通过目录关系返回位置。
